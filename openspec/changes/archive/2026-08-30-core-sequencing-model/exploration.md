# Exploration: core-sequencing-model

Step/Sequence/Scale/DeterministicRandom + PitchGenerator/RhythmGenerator,
Projucer-only, no GUI.

  `Source/Main.cpp` (JUCEApplication + DocumentWindow boilerplate),
  `Source/MainComponent.h/.cpp` (AudioAppComponent passthrough —
  `getNextAudioBlock` just clears the buffer). No `core/`, `generation/`, or

  `H:\Proyectos\Juce\Projucer\modules` (what `Berlin.jucer`'s exporters

## Affected areas

- `Source/core/Step.h`, `Source/core/Sequence.h(+.cpp)`,
  `Source/core/Scale.h(+.cpp)` — new domain types.
- `Source/core/MusicalTime.h` — new, scope-TBD (can be deferred without

- `Source/generation/DeterministicRandom.h`,
  `Source/generation/PitchGenerator.h/.cpp`,
  `Source/generation/RhythmGenerator.h/.cpp` — new.
- `Berlin.jucer` — needs new `<FILE>` entries for every new file (Projucer
  doesn't glob folders); then `Projucer.exe --resave Berlin.jucer` to
  regenerate the VS project.
- A new, separate `.jucer` for the test runner (cannot be a second exporter
  inside `Berlin.jucer` — see Approach 2 below).
- `Source/Main.cpp` / `Source/MainComponent.*` stay untouched this change
  (no GUI/playback wiring).

## Approaches

1. **Test runner: separate console-app `.jucer`** (e.g.
   `Tests/BerlinTests.jucer`) mirroring `JUCE/extras/UnitTestRunner`
   - Pros: exact working precedent on disk, minimal module deps
     (`juce_core` only), Main.cpp is a near-copy of a proven example,
     produces a real CI-friendly .exe (0/1 exit code), shares
     `Source/core`/`Source/generation` files by relative `<FILE>`
     reference — no code duplication.
   - Cons: two `.jucer` file-lists to keep in sync; a second VS solution to
     build.
   - Effort: Low-Medium.

2. **Second exporter/target inside `Berlin.jucer` itself**
   - Ruled out: `projectType` is document-wide and `<MAINGROUP>` (incl.
     `main()`) is shared across all exporters in one `.jucer`. A console
     test runner needs a different `projectType`/`main()` than the GUI
     app — not a real Projucer feature.
   - Effort: N/A (infeasible).

3. **RNG — `DeterministicRandom` wrapper over `juce::Random`** (recommended)
   vs. raw `juce::Random` everywhere vs. a third-party PRNG
   - Wrapper: zero new dependency, JUCE already guarantees
     seed-determinism, gives one enforced "always explicitly seeded"
     contract and a single test surface for the seed-reproducibility
     requirement. Raw `juce::Random`: same guarantee but no guardrail
     against accidentally using `getSystemRandom()`. Third-party PRNG:
     unnecessary dependency, not justified (the proposal itself warns
     against unneeded dependencies).
   - Effort: Low.

4. **`Step` field scope — full proposal-shaped struct now vs. pared-down
   (`note`+`active`) for just this phase**
   - Full: matches section 6 exactly, avoids later breaking changes, but
     leaves several fields untested this phase. Pared-down: every field is
     actually exercised/tested now (Strict-TDD-friendly), needs a small
     additive change later when Velocity/Gate/Mutation generators land.
   - Effort: Low either way — a scope decision, not a technical blocker.

## Recommendation

- Folder layout: `Source/core/{Step.h, Sequence.h(+.cpp), Scale.h(+.cpp)}` +
  `Source/generation/{DeterministicRandom.h, PitchGenerator.h/.cpp,
  RhythmGenerator.h/.cpp}`; defer `MusicalTime` to a later change.
- Test runner: Approach 1 — sibling `Tests/BerlinTests.jucer`
  (`projectType="consoleapp"`, `defines="JUCE_UNIT_TESTS=1"`,
  `juce_core`-only deps), `Tests/Source/Main.cpp` adapted from JUCE's own
  `UnitTestRunner` example, one `juce::UnitTest` subclass per domain area,
  regenerated headlessly via `Projucer.exe --resave`.
- RNG: Approach 3 — `DeterministicRandom` wrapping `juce::Random(int64
  seed)`, explicit-seed-only constructor, minimal surface (`nextInt`,
  `nextFloat`, `getSeed`).
- `PitchGenerator`: scale-based strategy only (motif/interval-weighted
  deferred), API `{ Scale, rangeLow, rangeHigh } → int
  generateNextNote(DeterministicRandom&)`. `RhythmGenerator`:
  probability/density-based only (Euclidean/polyrhythm deferred), API
  `{ numSteps, density } → Sequence generate(DeterministicRandom&)` (only
  `active` gate populated). No formal pipeline/orchestrator class yet —
  composing the two into a printable demo sequence is a plain loop in a
  test/demo file, not new production code.
- `Step` scope: recommend pared-down (`note`, `active`) for this phase,
  noting Velocity/Gate/Probability/Accent as explicit additive future work.

## Risks

- Every new file needs manual `<FILE>` registration in `Berlin.jucer` (and
  the new test `.jucer`) plus a `Projucer.exe --resave` — no
  folder-globbing; easy to silently forget and leave code unbuilt.
- Two `.jucer` file-lists (app + tests) must be kept in sync manually.
- `useGlobalPath="1"` means the actual JUCE modules directory used at
  build/resave time is a Projucer preference, not visible from the repo —
  two plausible candidates exist on this machine; `sdd-apply` should keep
  the new test `.jucer` using the same `useGlobalPath="1"` convention
  rather than hardcoding a path.
- Proposal-internal inconsistency on `MusicalTime` scope needs an explicit
  decision in `sdd-propose`.
- No test framework exists yet — this change must land the test-runner
  `.jucer` and get one green build before any Strict-TDD red/green cycle is
  possible; sequence that as task 1.
- Scope-creep risk: section 42's full pipeline (octave/velocity/probability
  /mutation) is broader than this change's Pitch+Rhythm-only boundary —
  should be stated explicitly out of scope in `sdd-propose`/`sdd-design`.
